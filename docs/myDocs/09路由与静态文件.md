# 09 路由与静态文件

代码入口：[Router.cpp](../../src/routing/Router.cpp)、[StaticFiles.cpp](../../src/http/StaticFiles.cpp)、[Server.cpp:17](../../src/server/Server.cpp#L17)。

## 路由注册与匹配

`Router::add()` 把模式按 `/` 拆为段。例如 `/api/users/{id}` 编译为两个固定段和一个参数段。只要求模式以 `/` 开头；不存在正则表达式、参数类型约束或专门的路由优先级算法。

`dispatch(HttpRequest&)` 的顺序如下：

1. HEAD 使用 GET 作为有效匹配方法，但请求对象里的 method 仍然是 HEAD。
2. 按注册顺序遍历 `routes_`，逐段匹配路径。
3. 路径匹配但方法不同，将路由方法加入 allowed 集合，继续查找。
4. 路径和方法都匹配，把捕获值填进 `request.params`，调用 handler 并返回。
5. 没有找到可执行路由但 allowed 非空，生成 `405 + Allow`。
6. 否则调用 fallback；没有 fallback 才由 Router 自身返回 404。

段比较会忽略空段，因此 `/api/users/` 可以匹配 `/api/users`。参数段匹配任意非空单段，`/api/users/abc` 会匹配 `{id}`；是否是整数由控制器判断。

如果多个路由都能匹配，最先注册的有效方法路由获胜。增加 `/api/users/me` 时，应注意它与先前的 `/api/users/{id}` 的注册顺序。

当前 405 分支无条件向 Allow 加入 HEAD；在项目已有 GET 路由的情形下通常合理，但若以后只注册 POST 某路径，Allow 仍会错误宣称支持 HEAD。

## API 与静态资源的分界

Server 注册五条用户路由、两条系统路由，再设置静态 fallback。只有“没有任何路由路径匹配”才进入静态文件路径，不是所有非 200 API 都自动尝试文件。

| 请求 | 处理路径 |
| --- | --- |
| GET `/api/users` | 用户列表接口 |
| DELETE `/api/users` | 已匹配路径但方法不支持，Router 返回 405 |
| GET `/api/users/abc` | 参数路由匹配，控制器返回整数校验 400 |
| GET `/api/unknown` | 没有路径匹配，尝试根路径下 `api/unknown` 或 `.html` 文件 |
| GET `/about` | 静态处理器，通常读取 about.html |
| POST `/about` | 静态处理器首先拒绝方法，返回 405 |

API 前缀并未整体保留；未注册的 `/api/...` 也会进入静态 fallback。

## 静态处理器的完整流程

构造时通过 `canonical(documentRoot)` 保存根路径的规范绝对路径，失败就抛异常。但代码没有额外要求该路径一定是目录，已有普通文件也可能通过这一步。

```text
handle(request)
  → 只允许 GET/HEAD，否则 405 + Allow: GET, HEAD
  → resolve(request.path)
       → 去掉开头的 /
       → root_ / relative
       → weakly_canonical
       → 验证规范路径前缀及路径分隔符边界
  → resolve 失败：403
  → 是目录：追加 index.html
  → 不存在且无扩展名：尝试追加 .html
  → 不是普通文件：404
  → 取得文件大小，失败：500
  → 大于 32 MiB：413
  → 二进制方式打开并完整读取，失败：500
  → 200 + Content-Type + Cache-Control: no-cache
```

大小检查是 `size > 32 * 1024 * 1024`，所以恰好 32 MiB 在大小这一项上允许。目录没有 index.html 时返回 404，不生成目录列表，也没有为缺少尾部 `/` 做重定向。

`HEAD` 仍然读取文件并构建完整正文，由连接层在网络序列化时省略正文。这确保长度一致，但不会节省文件读取成本。

## 文件路径示例

假设根路径是 `D:/site/public`，并存在 `index.html`、`about.html`、`assets/style.css`：

| URL 路径 | 候选文件 | 说明 |
| --- | --- | --- |
| `/` | `public/index.html` | 目录首页 |
| `/about` | `public/about`，再尝试 `public/about.html` | 仅当原文件不存在且没有扩展名时补全 |
| `/about.html` | `public/about.html` | 直接文件 |
| `/assets/style.css` | `public/assets/style.css` | 嵌套路径 |
| `/assets/` | `public/assets/index.html` | 没有该首页就 404 |
| `/../secret.txt` | 正常解析后为 `public/secret.txt` | 父目录段已被 HTTP 层规整掉 |

扩展名补全不是通用内容协商：不会尝试 `.json`、`.htm`，也不会自动选择语言版本。

## MIME 与响应

`mimeTypeForExtension()` 将扩展名小写后查询表。HTML、CSS、JS、JSON、常见图片、字体、PDF、ZIP 等都有映射；未知类型返回 `application/octet-stream`。

文本类的部分 MIME 带 `charset=utf-8`，但读取操作不会将文件编码转换成 UTF-8。没有 ETag、Last-Modified、Range 解析、压缩、分块或流式发送。

读文件按事先取得的大小分配字符串，读取后按 `gcount()` 缩小；只在 `file.bad()` 时报告读取错误。并发修改文件可能影响最终内容，代码没有建立文件快照或执行完整一致性校验。

## 路径检查的能力和缺口

已经实现两层处理：URL 层规整点段，文件层对候选路径做 weakly_canonical 后检查根路径前缀，并验证前缀后面的分隔符，防止把 `public2` 当作 `public` 的子目录。

但文件层只检查最初的候选路径。此后追加 `index.html` 或 `.html` 时，没有对最终路径重新执行边界检查。从源码可推导：根目录内的默认首页或补全得到的 HTML 如果是指向根目录外的符号链接，可能沿链接读取外部文件。

此外，检查路径与真正打开文件不是一个原子操作；文件系统内容可能在两者之间改变。本次没有创建符号链接或运行复现，不能写成已实测的漏洞结果，详细分析见 [15静态审查问题与改进方向](15静态审查问题与改进方向.md)。
