# 02 构建与运行

以下命令是从构建文件和入口代码整理的操作说明，**本次未执行编译、启动或测试**。

## 构建系统和外部依赖

[CMakeLists.txt](../../CMakeLists.txt) 要求 CMake 3.20 以上、C++20，并关闭编译器语言扩展。单配置生成器未指定构建类型时使用 Release；Visual Studio 这类多配置生成器在构建时选择 `--config`。

| 依赖 | 用途 |
| --- | --- |
| 支持 C++20 的编译器和标准库 | `std::thread`、`filesystem`、`shared_mutex`、`variant`、`from_chars` 等 |
| CMake 和对应构建工具 | 生成并执行构建；例如 Visual Studio/MSBuild、Ninja 或 Make |
| `Threads::Threads` | CMake 查找的系统线程支持，属于系统依赖 |
| Windows 的 `ws2_32` | Winsock 系统库 |

仓库没有依赖 Boost、Asio、第三方 JSON 库或第三方测试框架，也没有配置阶段下载依赖的逻辑。README 列出的工具链建议是 Windows VS 2022，以及 Linux GCC 13+/Clang 16+；这些版本下的可用性未在本次重新验证。

## 构建目标与程序入口

| 目标 | 入口 | 职责 |
| --- | --- | --- |
| `httpserver_core` | 无 `main()` | 复用全部服务器模块的核心库 |
| `httpserver` | [src/main.cpp:36](../../src/main.cpp#L36) | 参数、配置、日志、Server 生命周期 |
| `benchmark_client` | [BenchmarkClient.cpp:109](../../tools/BenchmarkClient.cpp#L109) | 多连接闭环请求客户端 |
| `unit_tests` | [TestFramework.cpp:26](../../tests/TestFramework.cpp#L26) | 链接八个单元测试文件 |
| `integration_tests` | 同一个测试框架入口 | 启动真实 Server 并通过 socket 验证 |

`BUILD_TESTING` 默认是 `ON`；设置为 `OFF` 会去掉两个测试程序，不会去掉压测客户端。CMake 只注册两个 CTest 项目：`unit` 和 `integration`，并非给每个 `TEST(...)` 单独注册一个 CTest 项。

编译 `httpserver` 的构建后步骤会把 `public/` 和 `server.conf` 复制到该可执行文件所在目录。仅构建 `unit_tests` 不会触发这个步骤。不要把输出目录内的配置文件当成唯一配置副本，后续构建可能再次复制仓库版本。

## Windows 构建说明

在具有 VS 2022 C++ 工具链和 CMake 的 PowerShell 环境中：

```powershell
Set-Location 'D:\workSpace\cpp-http-server'
cmake -S . -B build/windows -G "Visual Studio 17 2022" -A x64
cmake --build build/windows --config Release
```

预期输出目录是 `build\windows\Release`。仓库当前还存在 CLion 生成的 `cmake-build-debug`；其缓存指向 CLion 附带的 MinGW 和 Ninja，这是另一套工具链配置，不能把它与 Visual Studio 的构建缓存混用。

使用 CLion 时，可在项目 CMake 配置中选择工具链和 `httpserver` 目标，并把运行工作目录设置为包含 `server.conf`、`public` 的目录，或显式传入绝对路径参数。

## Linux 构建说明

在具备 CMake、C++ 编译器和 Make/Ninja 的环境中：

```bash
cmake -S . -B build/linux -DCMAKE_BUILD_TYPE=Release
cmake --build build/linux --parallel
```

输出程序通常为 `build/linux/httpserver`、`benchmark_client` 和两个测试程序。Windows 与 Linux 应使用不同构建目录；两者的缓存和二进制格式不同。

## 最小启动方式

Windows，已有上述构建产物时：

```powershell
Set-Location 'D:\workSpace\cpp-http-server\build\windows\Release'
.\httpserver.exe
```

Linux，从仓库根目录开始：

```bash
cd build/linux
./httpserver
```

使用示例配置时，预期监听 `127.0.0.1:8080`，浏览器访问 `http://127.0.0.1:8080/`。可以在另一个终端检查健康接口；以下命令仅供手动操作：

```powershell
curl.exe -i http://127.0.0.1:8080/api/health
```

预期为 200 和 `{"status":"ok"}`。正常退出方式是终端中按 Ctrl+C，具体停止过程见 [12日志指标与退出](12日志指标与退出.md)。

## 工作目录是启动时最容易出错的地方

代码直接打开 `server.conf` 和 `./public`，没有根据可执行文件所在目录重新定位。因此“把资源复制到程序旁边”和“程序自动从自身目录找资源”是两件不同的事。

例如，在仓库根目录运行 `build/windows/Release/httpserver.exe`，默认读到的是仓库根目录的配置和 `public`；切换到 Release 目录后运行，读到的才是复制出的文件。

相对 `document_root` 也不是相对配置文件目录解析。以下方式可消除工作目录歧义：

```powershell
& 'D:\workSpace\cpp-http-server\build\windows\Release\httpserver.exe' `
  --config 'D:\workSpace\cpp-http-server\server.conf' `
  --root 'D:\workSpace\cpp-http-server\public' `
  --port 8081
```

## 参数、启动错误和返回码

| 参数 | 作用 |
| --- | --- |
| `--help` / `-h` | 打印帮助，返回 0 |
| `--config <path>` | 选择配置文件；默认 `server.conf` |
| `--port <number>` | 覆盖端口；当前解析校验弱于配置文件 |
| `--root <path>` | 覆盖静态根路径 |
| `--log-level <level>` | 覆盖日志级别 |

未知参数、缺少参数值、非法命令行日志级别返回 2；配置读取/解析异常、非法端口转换异常、Server 初始化或监听异常返回 1。正常停止返回 0。

有两个特殊行为需要记住：显式指定但打不开的配置文件仍会回退默认值；配置中的错误会在命令行覆盖之前触发，所以 `--port` 不能挽救一个已经包含非法端口的配置文件。根路径不存在会在 Server 构造阶段失败，而不是等到收到请求才报错。
