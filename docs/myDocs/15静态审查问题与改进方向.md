# 15 静态审查问题与改进方向

以下结论基于提交 `2733afe` 的源码阅读，**未编译、未运行复现、未修改业务实现**。此处区分可直接确认的控制流缺口与需要平台/时序验证的结果，避免把设计意图当作实现保证。

## 1. 静态文件补全后没有重新检查最终路径

位置：[StaticFiles.cpp:95](../../src/http/StaticFiles.cpp#L95)。

当前顺序是 `resolve(path)` 做 canonical 和根边界检查，然后目录追加 `index.html`，或无扩展名路径尝试 `.html`，最后直接打开文件。

从代码可推导两个需要验证的例子：

- 临时根路径的 `index.html` 是指向根外 `secret.txt` 的符号链接。请求 `/` 时，最初通过检查的是根目录，随后追加的链接没有再做边界验证。
- 根路径下 `about` 不存在，`about.html` 是指向外部普通文件的链接。请求 `/about` 先验证不存在的候选路径，再补成链接并尝试读取。

对同一个 `about.html` 直接请求完整文件名时，会在最初 resolve 中解析链接并进行边界检查；因此直接路径与补全路径可能表现不同。现有测试没有符号链接用例，不能借用点段穿越测试证明这两条分支安全。

建议：完成首页/扩展名选择后，再对最终候选做规范化和根路径归属检查，并增加对应测试。若还要防止检查到打开之间的文件系统变更，需要更进一步的文件打开策略，仅增加一次字符串检查不足以解决所有时序问题。

## 2. 配置来源之间校验不一致

位置：[Config.cpp:66](../../src/config/Config.cpp#L66)、[main.cpp:83](../../src/main.cpp#L83)。

文件端口严格检查范围，命令行却使用 `static_cast<uint16_t>(stoi(...))`，没有检查剩余字符或范围。`--port 70000` 可转成 4464，`--port 8080abc` 可接受数字前缀。

大小和队列参数在部分路径中先从 long long 转成 size_t，再进行有限检查；负数因此可能变成很大的无符号数。若干 int 字段也缺少缩窄前的范围判断。`max_requests_per_connection=0` 没被禁止，却使连接处理循环直接跳过。

建议：数值转换前校验范围；所有来源覆盖完成后统一验证最终 Config；针对 0、负数、极值、尾随字符、CLI 与文件一致性分别补测试。

## 3. 显式指定缺失配置仍会回退

位置：[main.cpp:75](../../src/main.cpp#L75)。

`--config` 指定的路径与默认 `server.conf` 共用探测逻辑，文件不存在或无法打开时都提示使用默认值。直接调用 `loadFromFile()` 才会得到打不开文件的异常。

这个行为可能使配置路径拼错后仍以另一套参数启动。若要区分“默认配置可选”和“用户显式指定必须存在”，需要在参数解析时保存是否显式提供过 --config。现有测试只覆盖后者函数的异常，不覆盖主程序回退行为。

## 4. 部分流水线请求的超时标记错误

位置：[Connection.cpp:63](../../src/net/Connection.cpp#L63)、[Connection.cpp:81](../../src/net/Connection.cpp#L81)。

当前先把 pending 喂给解析器，再设置：

```cpp
bool receivedAnything = state != ParseState::NeedMore;
```

如果 pending 非空但只是下一请求的一部分，解析状态仍为 NeedMore，receivedAnything 却为 false。若客户端此后不再发送，连接可能按 keep-alive 空闲预算等待，并在到期后静默关闭，未走部分请求的 408 分支。

建议：明确记录是否已给当前解析器喂入字节，用此信息选择请求/空闲预算；在一个 TCP 发送中构造“完整请求 A + 部分请求 B”，之后暂停输入，补连接级测试。现有 parser leftover 测试只覆盖完整下一请求。

## 5. 停止流程没有统一的时间上限

位置：[Connection.cpp:83](../../src/net/Connection.cpp#L83)、[Server.cpp:50](../../src/server/Server.cpp#L50)、[Server.cpp:105](../../src/server/Server.cpp#L105)。

可以直接确认：停止标志只在 receive 返回 Timeout 的分支观察；正在执行的 handler 不可取消；线程池继续领取队列中的连接；接收线程上的 503 发送未设置超时。

这些因素使整体退出耗时依赖客户端、队列、磁盘和发送状态，不能由 250 ms 接收切片推出固定上限。具体拖延多久需要运行与时序验证，本次没有时间测量。

建议：定义停止期间对新请求、排队连接和在途响应的策略；在循环入口等位置检查停止条件；给所有发送路径提供合适的期限；用空闲、慢发送、持续输入和长队列分别验证。

## 6. 同一 Server 停止后不能正常再次启动

位置：[Server.cpp:35](../../src/server/Server.cpp#L35)、[ThreadPool.cpp:33](../../src/threading/ThreadPool.cpp#L33)。

stop 调用线程池 shutdown 后，`stopping_` 保持 true，workers 被清空。start 只重新绑定监听并创建接收线程，没有重建线程池。由此推导，第二次启动接收到的连接会因 submit 失败进入 503 路径。

建议：明确禁止同一实例重启，或增加完整的状态机并重建必要资源。当前文档应把它表述为一次启动周期，而不是通用可重启服务对象。

## 7. HTTP 校验和头部语义是简化实现

位置：[HttpParser.cpp:145](../../src/http/HttpParser.cpp#L145)、[HttpRequest.cpp:63](../../src/http/HttpRequest.cpp#L63)、[Router.cpp:93](../../src/routing/Router.cpp#L93)。

| 可确认的实现细节 | 影响与建议 |
| --- | --- |
| Host 仅检查是否存在 | 空值、重复值未被完整拒绝，应补值和数量校验 |
| Connection 按完整字符串比较 | 不支持 token 列表；应拆分并优先处理 close |
| 头部值、原始路径缺少完整控制字符检查 | “严格解析”只能限定在当前已有检查项内 |
| Router 的 405 分支无条件添加 HEAD | 未来只有 POST 的路径也可能错误宣称支持 HEAD，应依据是否有 GET 决定 |
| HEAD 正文抑制只在正常分支 | 解析失败、408、503 没有一致的无正文策略 |

这些问题不影响阅读正常 GET 流程，但决定了服务器不能被描述成完整 HTTP 合规实现。协议边界用例见 [13测试映射与边界验证](13测试映射与边界验证.md)。

## 8. JSON 解析和数字序列化仍需加固

位置：[Json.cpp:176](../../src/json/Json.cpp#L176)、[Json.cpp:245](../../src/json/Json.cpp#L245)、[Json.cpp:36](../../src/json/Json.cpp#L36)。

字符串分支会直接追加非反斜杠字节，没有拒绝全部原始控制字符。数字分支主要依赖 stod，可能接受 `+1`、前导零等不符合严格 JSON 数字语法的形式。代理对没有合并为对应字符，重复键查找返回第一个值。

`appendNumber()` 判断整数前先转 long long，没有先检查有限数是否处在该类型的可表示范围；极大有限数存在越界转换问题。对程序直接构造的非有限 double，也缺少明确的合法 JSON 输出策略。

建议：先建立严格输入语法和数值范围，再实现转换；为字符串控制字符、数字边界、代理对、重复键和深度阈值增加有区分力的测试。

## 9. 测试和压测工具有自己的观察边界

位置：[test_integration.cpp:218](../../tests/test_integration.cpp#L218)、[BenchmarkClient.cpp:36](../../tools/BenchmarkClient.cpp#L36)、[TestFramework.cpp:26](../../tests/TestFramework.cpp#L26)。

长连接集成用例对每个响应只 receive 一次，容易受到 TCP 分片影响；压测客户端把收齐任意状态码的完整响应算作 completed；测试名筛选没有命中任何用例也会返回成功码。

建议：长连接测试按响应边界完整读取；压测单独统计 HTTP 状态类别和成功业务数；过滤后零用例时明确提示或失败。不能只看工具退出码或 requests/sec 就得出覆盖完整、服务成功率高的结论。
