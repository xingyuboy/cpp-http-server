# 10 用户接口与上传删除边界

代码入口：[UserController.cpp](../../src/api/UserController.cpp)、[UserStore.cpp](../../src/api/UserStore.cpp)、[SystemController.cpp](../../src/api/SystemController.cpp)、[Json.cpp](../../src/json/Json.cpp)。

## 实际提供的接口

| 方法和路径 | 处理函数 | 正常结果 | 常见错误 |
| --- | --- | --- | --- |
| GET `/api/users` | `listUsers` | 200，`users` 数组和 `count` | 可选 `?name=` 大小写敏感子串过滤 |
| GET `/api/users/{id}` | `getUser` | 200，单个用户对象 | ID 不能完整解析为 int：400；不存在：404 |
| POST `/api/users` | `createUser` | 201，用户对象及 Location | 正文或字段不合法：400 |
| PUT `/api/users/{id}` | `replaceUser` | 200，替换后的对象 | ID/正文错误：400；不存在：404 |
| DELETE `/api/users/{id}` | `deleteUser` | 204，无正文 | ID 错误：400；不存在：404 |
| GET `/api/health` | 注册时的 lambda | 200，`{"status":"ok"}` | 不检查数据库或外部系统 |
| GET `/api/benchmark` | 注册时的 lambda | 200，指标快照 | 指标口径见 12 |

正常 HEAD 请求会复用对应 GET 路由，只在连接层发送时去掉正文。控制器返回的业务错误是 `{"error":"..."}` JSON；路由层或解析层错误通常是 HTML，调用客户端不能假定所有错误响应都能按 JSON 读取。

## 创建用户的纵向链路

```text
HTTP POST + Content-Length
  → RequestParser 得到 body
  → Router 匹配 /api/users
  → UserController::createUser
  → readUserInput
       → 可选检查 Content-Type
       → json::parse
       → 读取 name、email
  → UserStore::create
       → unique_lock
       → nextId_++
       → users_.emplace
  → json::serialize
  → HttpResponse::json(201) + Location
  → Connection 统一发送
```

创建后的 Location 为 `/api/users/<id>`。新建存储会预置 ID 1 的 Alice 和 ID 2 的 Bob，因此没有其他写入时首次创建得到 ID 3。

## 输入校验的真实范围

| 输入项 | 当前处理 |
| --- | --- |
| Content-Type 缺失 | 仍尝试解析 JSON |
| Content-Type 存在 | 只做大小写敏感的 `application/json` 子串查找，不是完整媒体类型解析 |
| Content-Type 不匹配 | 返回 400，不是 415 |
| name | 必须存在、必须是字符串、不能是空字符串 |
| name 只含空格 | 后端不 trim，非空即可通过；前端页面另外做了 trim |
| email | 可省略，省略后为空字符串；存在时必须是字符串，不检查邮箱格式 |
| 多余字段 | 忽略 |
| PUT 省略 email | 替换成空字符串，而不是保留旧值 |
| id 为 0 或负数 | 可以作为整数解析，通常因没有对应用户返回 404 |

`PUT` 是这里定义的用户字段替换操作，不支持 PATCH，也不在目标缺失时自动创建用户。

## 存储和删除

`UserStore` 使用 `map<int, User>`，`list/find/size` 使用共享锁，`create/update/remove` 使用独占锁。删除的核心操作是：

```cpp
return users_.erase(id) > 0;
```

它只移除内存 map 中的记录。删掉 ID 3 后，下次创建继续使用递增 ID，不会填补空位。进程结束后数据丢失；再次创建 Server 会重新生成两条种子数据。

删除接口没有认证或授权逻辑。这里没有数据库事务、软删除、恢复、审计表或持久化文件。

## 上传文件和删除文件是否支持

**当前不支持文件上传，也不支持通过 HTTP 删除磁盘文件。**

源码证据是：路由只注册用户和系统接口；`readUserInput()` 只读取 JSON 字段；`StaticFileHandler` 只接受 GET/HEAD；`UserStore::remove()` 只对 map 调用 erase；生产代码没有上传正文落盘或删除静态文件的业务流程。

测试中的 `ofstream`、`create_directories`、`remove_all` 用于准备和清理临时测试文件，不能当成文件管理功能。日志器写日志文件也不属于上传接口。

在请求报文合法、没有 Transfer-Encoding、正文未超过限制的前提下：

| 请求 | 从代码推导的结果 | 原因 |
| --- | --- | --- |
| POST `/upload`，携带文件字节 | 405 | 无注册路由，静态 fallback 拒绝 POST |
| POST `/api/users`，Content-Type 为 multipart/form-data | 400 JSON | 用户输入类型检查失败 |
| DELETE `/index.html` | 405，磁盘文件不变 | 静态处理器只允许 GET/HEAD |
| DELETE `/api/users/1` | 204，内存用户被移除 | 调用 UserStore::remove |
| 再次 DELETE `/api/users/1` | 404 | 用户已不存在 |

若请求先违反协议或体积限制，则可能更早得到 400、413、501，不会到达上表的业务路径。

如果以后扩展上传，需要另行设计路由、正文格式、写入策略、名称生成、大小配额和最终路径校验；扩展文件删除也需要独立定义文件标识与权限规则。这些都是后续设计点，不是当前已有实现。

## JSON 模块值得学习的部分

JSON 值使用 variant，数组使用 vector，对象使用保留插入顺序的键值对 vector。递归下降解析器处理对象、数组、字符串、数字、布尔和 null，失败可返回包含偏移的错误文本，代码设置了深度阈值 `kMaxDepth = 64`。

它是简化实现：数字统一为 double；对象允许重复键而 `find()` 取第一个；Unicode 转义中的代理码元各自转成替换字符；数字解析借助 `stod`，字符串也未完整拒绝原始控制字符。不能将它视作完整的严格 JSON 校验器。
