## 测试框架怎么运行

[TestFramework.hpp](../../tests/TestFramework.hpp) 的 `TEST(name)` 定义函数，并通过静态 Registrar 加入 registry。两个测试程序都使用 [TestFramework.cpp](../../tests/TestFramework.cpp) 中的 main。

- `CHECK`、`CHECK_EQ`：记录失败，继续当前用例。
- `REQUIRE`：记录失败后返回当前测试函数，用于避免后续空指针等连锁错误。
- 测试抛出异常：框架捕获并记失败。
- 可执行文件的第一个参数是用例名的**大小写敏感子串**，不是正则表达式。
- 所有被选中的用例无失败，程序返回 0；否则返回 1。

一个容易漏看的细节：过滤器没有匹配任何用例时，也会以 `0/0 tests passed` 返回 0。查看运行数量才能确认目标测试确实被选中。

## 集成测试如何隔离环境

`ServerFixture` 在系统临时目录创建 `public/index.html`，根路径外再放 `secret.txt`，程序化设置 `port = 0`、4 个工作线程、1000 ms 请求和长连接超时，然后 start。析构先 stop，再清理自己创建的临时目录。

辅助函数 `exchange()` 用真实 socket 发送原始请求，按响应头分隔符和 Content-Length 收取响应；它没有复用服务器的请求解析器，但复用了 socket 封装。因此它可以发现收发链路集成问题，并非完全独立于所有底层实现的黑盒客户端。

15 个用例覆盖静态首页、用户列表/创建/删除、HEAD、404、405、非法报文、未知方法、越界尝试、超大正文、408、同连接两次请求、16 客户端并发、指标读取。

`IntegrationKeepAliveServesTwoRequestsOnOneSocket` 只对每个响应调用一次 receive，假定能在那次读取里拿到相关状态行和头部。这对 TCP 分片不够稳健；不能因为该用例存在就认定长连接的所有分片组合都覆盖了。

## 原始报文：验证解析错误与边界

curl 可能规整路径、补 Host 或推导 Content-Length。观察畸形请求时应直接发送字节，避免客户端帮忙修复。下面是一段**未执行**的 Python 手工探针示例，修改 request 即可用于独立本地实例：

```python
import socket

# 缺少 Host，预期进入 HTTP/1.1 的 400 分支。
request = b"GET / HTTP/1.1\r\nConnection: close\r\n\r\n"
with socket.create_connection(("127.0.0.1", 8080), timeout=3) as client:
    client.settimeout(8)
    client.sendall(request)
    chunks = []
    while True:
        try:
            chunk = client.recv(4096)
        except socket.timeout:
            print("客户端等待超时；服务端可能尚未结束响应")
            break
        if not chunk:
            break
        chunks.append(chunk)
    print(b"".join(chunks).decode("utf-8", errors="replace"))
```

除专门测长连接外，合法请求增加 `Connection: close`，便于探针读到 EOF。测试半个请求的 408 时不要提前 shutdown 客户端写方向；否则服务端可能把 EOF 当成主动断连并直接返回。

| 输入构造，未特殊说明时补齐 Host 和 CRLF 结束符 | 静态预期 | 决策位置 |
| --- | --- | --- |
| `GET / HTTP/1.1`，不发 Host | 400 | `applyHeaders` |
| `PATCH / HTTP/1.1` | 501 | 方法识别 |
| `GET / HTTP/2.0` | 505；这是文本版本校验，不是 HTTP/2 协议测试 | 请求行解析 |
| 路径 `/%zz` 或 `/%00` | 400 | percentDecode |
| `Transfer-Encoding: chunked` | 501 | applyHeaders |
| `Content-Length: abc`、负数或重复该头 | 400 | 长度解析 |
| `Content-Length: 99999999`，不必发送正文 | 413 | 声明长度超过限制 |
| 头部累计超过 8192 字节 | 413 | consume 头部检查 |
| target 为 `/` 加 2048 个 a，总长 2049，头部总长保持小于 8192 | 414 | target 长度检查 |
| 完整头部声明 Content-Length 为 5，只发 `ab` 并停顿 | 默认配置下经过停顿期限后 408 | Connection 的部分请求超时 |
| 建连后完全不发送 | 到期静默关闭，通常没有 HTTP 响应 | Connection 空闲分支 |
| `Host:` 值为空或重复 Host | 当前检查仅判断存在，可能进入业务处理 | 待增强校验 |
| `Connection: keep-alive, close` 的 HTTP/1.1 请求 | 当前 keepAlive 返回 true；观察后需主动结束测试连接 | 整值比较缺口 |

观察“字段刚好达到上限”和“超过一字节”比只发送超大输入更能定位边界。完整头部总长度恰好等于限制时通过大小检查，超过则失败；目标长度、声明正文长度也是超过上限才拒绝，前提是其他语法合法。

## 配置、并发与退出的待验证场景

每个场景应使用单独的学习配置或临时根路径，先恢复基线再改变一个变量。无需修改仓库业务源码。

| 场景 | 操作设计 | 从代码推导的观察点 |

| 主程序缺失配置 | 指定不存在的 --config，并传入有效 --root | 提示使用默认值，继续尝试启动 |
| 文件与 CLI 校验差别 | 文件 port=70000；另一次使用 --port 70000 | 前者报错，后者转为 4464 后尝试绑定 |
| 禁止零请求数的缺失检查 | 配置 max_requests_per_connection=0 | 当前可启动但连接任务不处理请求 |
| 单连接请求上限 | 配置上限为 1，发一个 HTTP/1.1 请求 | 首个正常响应应标记 Connection: close |
| 停顿超时 | request_timeout=1000，发半个请求后停顿 | 预期 408；总耗时需实测，不能精确承诺 1000 ms |
| 持续小流量 | 每次在请求超时前追加少量字节 | 期限重置，不是绝对请求期限 |
| 队列满 | `worker_threads=1`、`max_queued_connections=1`；确认首连接占住线程、第二个排队，再连接第三个 | 第三个得到 503 和 Retry-After: 1；需同步安排避免调度竞态 |
| 退出空闲连接 | 保持空闲长连接后 Ctrl+C | 经接收切片观察停止，记录整体耗时 |
| 退出排队连接 | 多个连接排队，再 Ctrl+C | 队列分批领取，不能推定整体只需 250 ms |
| 处理器异常 | 在独立测试夹具 start 前注册抛 runtime_error 的路由 | 连接层应转换为 500；当前仓库没有这一专用集成用例 |
