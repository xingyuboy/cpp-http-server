# 07 套接字封装与连接管理

代码入口：[Socket.hpp](../../src/net/Socket.hpp)、[Socket.cpp](../../src/net/Socket.cpp)、[Connection.hpp](../../src/net/Connection.hpp)、[Connection.cpp](../../src/net/Connection.cpp)。

## 先区分三个角色

| 角色 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| `TcpListener` | 创建监听 socket、绑定、监听、接受客户端 | 不解析 HTTP |
| `TcpSocket` | 已连接句柄的收发、超时设置、关闭和移动所有权 | 不选择业务处理器 |
| `serveConnection` | 使用 socket 执行完整 HTTP 会话 | 不管理工作线程的创建 |

监听 socket 用于获得新的连接 socket，实际 HTTP 数据从后者读取。一个连接可以包含多个请求；`recv()` 每次返回的字节数也不对应完整请求边界。

## 跨平台封装

| 事项 | Windows | 非 Windows 分支 |
| --- | --- | --- |
| 句柄和无效值 | `SOCKET` / `INVALID_SOCKET` | `int` / `-1` |
| 初始化 | 函数内静态 `WinsockGuard` 调用 WSAStartup | 无初始化动作 |
| 关闭 | `closesocket` | `close` |
| 半关闭写方向 | `SD_SEND` | `SHUT_WR` |
| 读取错误号 | `WSAGetLastError` | `errno` |
| 超时参数 | `DWORD` 毫秒 | `timeval` 秒和微秒 |
| select 第一个参数 | 传 0 | 监听句柄 + 1 |
| 发送到断开连接 | 依靠 Winsock 错误返回 | send 使用 `MSG_NOSIGNAL` |

`ensureNetworkReady()` 在 `bindAndListen()`、`connectTcp()` 内调用。调用者无需在 `main()` 里手动初始化 Winsock，测试程序和压测客户端也能走同一套初始化路径。

## 监听调用链

```text
bindAndListen(address, port, backlog)
  → ensureNetworkReady
  → getaddrinfo：AF_INET + SOCK_STREAM + IPPROTO_TCP
  → socket
  → 非 Windows 设置 SO_REUSEADDR
  → bind
  → listen
  → 用 TcpSocket 保存句柄

acceptWithTimeout(timeoutMs, peer)
  → select 等待监听 socket 可读
  → accept 获得连接 socket
  → getnameinfo 取得数字地址和端口
  → optional<TcpSocket>
```

`AF_INET` 将服务限制为 IPv4。`getaddrinfo` 结果只使用第一个条目，没有逐个地址回退。`localPort()` 通过 `getsockname()` 得到真实端口，主要服务于端口 0 的测试场景。

接收轮询超时、select 错误或 accept 失败都可能表现为 `nullopt`，接收循环不会区分原因。不能把每次空结果都解释为“没有客户端”。

## RAII 与收发结果

`TcpSocket` 析构调用 `close()`。移动构造把源句柄设为无效值；移动赋值先关闭自身旧句柄，再接管新句柄。因此连接处理函数的提前返回和异常退出都能释放资源。

| `IoStatus` | `receive` 含义 | `sendAll` 含义 |
| --- | --- | --- |
| `Ok` | 读到大于 0 个字节 | 全部待发字节已交给 send |
| `Closed` | 对端关闭或映射为断连的错误 | 断连，可能已发送部分字节 |
| `Timeout` | socket 接收等待超时 | 发送等待超时，保留已发送数量 |
| `Error` | 其他系统错误 | 其他系统错误，保留已发送数量 |

`receive()` 遇到中断错误会重试。`sendAll()` 循环累加已发送字节，解决单次 send 未发完整报文的情况；`Ok` 表示本端 send 成功，不是对端应用已经消费或确认处理。

`setReceiveTimeout`、`setSendTimeout`、`setNoDelay` 当前没有检查 `setsockopt` 返回值，因此“调用了设置函数”不等于已确认操作系统成功应用设置。

## 长连接和流水线请求

连接层每次只处理一个请求。解析器可能一次收到完整请求 A 和请求 B 的部分或全部字节，`leftover()` 暴露 B 的字节，连接层复制进 `pending` 并交给下一个解析器。

这就是当前流水线支持的含义：已经收到的后续请求不会丢失，并按顺序处理；没有在同一连接内并行执行请求。

正常响应的 keep-alive 条件是：

```cpp
const bool keepAlive = request.keepAlive() && !lastRequest;
```

HTTP/1.1 默认保持，HTTP/1.0 默认关闭；精确匹配的 `Connection: close` 或 `keep-alive` 可以覆盖默认值。到达单连接请求上限后强制关闭，即使客户端要求继续保持。

当前 `keepAlive()` 只比较整个头值，不解析逗号分隔 token。因此 `Connection: keep-alive, close` 不会按其中的 close token 处理，详见 [15静态审查问题与改进方向](15静态审查问题与改进方向.md)。

## 超时实际限制什么

| 场景 | 等待预算 | 当前处理 |
| --- | --- | --- |
| 新连接尚未发任何字节 | `requestTimeoutMs` | 到期静默关闭，不回 408 |
| 已处理请求，等待下一请求 | `keepAliveTimeoutMs` | 到期静默关闭 |
| 当前请求收到新字节 | 从此刻重新计算 `requestTimeoutMs` | 有进展就延长截止时间 |
| 收到部分请求后停止发送 | 请求停顿期限 | 正常标记路径下发送 408 后关闭 |
| receive 的一次等待超时且 Server 已停止 | 最多 250 ms 的切片观察点 | 提前退出连接循环 |

接收的单次 socket 超时设为 `min(250, idleBudgetMs)`，用 `steady_clock` 检查真正截止时间。它不是整条请求的绝对完成期限：客户端持续少量发送数据会不断刷新期限。

请求在工作队列里等待的时间不算在这个期限内，计时从工作线程执行连接任务后开始。系统调度和 socket 超时粒度也可能带来额外等待。

`pending` 中已经存在不完整下一请求时，当前实现可能错误地把它当成空闲等待，并在到期后静默关闭；这也是为什么需要单独覆盖“半个流水线请求”的测试。

## 关闭与客户端连接函数

正常的最终响应、解析错误和请求超时路径会调用 `shutdownWrite()`，通知对方写方向结束，随后函数返回时析构关闭句柄。半关闭表达发送完成意图，但不能保证任意平台和任意未读输入条件下都不发生重置。

`connectTcp(host, port, timeoutMs)` 供集成测试和压测客户端使用。代码先执行阻塞 `connect()`，成功后才设置收发超时，因此参数 `timeoutMs` 不是 TCP 建连的总时间上限。

没有专门的 `test_socket.cpp`；socket 行为主要通过 [test_integration.cpp](../../tests/test_integration.cpp) 间接验证。现有测试也没有系统覆盖 partial send、setsockopt 失败或阻塞 connect 的时限。
