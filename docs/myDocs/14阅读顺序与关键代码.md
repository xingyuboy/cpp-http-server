## 第一条精读调用链：静态页面

```text
main
  → Server::Server：安装静态 fallback
  → Server::start
  → TcpListener::bindAndListen
  → Server::acceptLoop
  → TcpListener::acceptWithTimeout
  → ThreadPool::submit
  → ThreadPool::workerLoop
  → serveConnection
  → TcpSocket::receive
  → RequestParser::consume
  → Router::dispatch
  → StaticFileHandler::handle
  → HttpResponse::serialize
  → TcpSocket::sendAll
```

实际输入可选 `GET /about HTTP/1.1`，Host 为 localhost。阅读时依次写下 `buffer_`、`request.path`、文件候选路径、`response.body()` 和最终报文长度，不需要运行也能完成一轮数据追踪。

## 第二条精读调用链：创建与删除用户

```text
POST /api/users
  → consume 依据 Content-Length 收完整正文
  → dispatch 匹配 POST 路由
  → createUser → readUserInput → json::parse
  → store.create：加锁、分配 ID、写入 map
  → 201 + Location + JSON 正文

DELETE /api/users/<id>
  → dispatch 捕获 params["id"]
  → deleteUser → parseId
  → store.remove：加锁、erase
  → 204 无正文
```

随后在相同对象上 GET 该 ID，应沿用户查询路径得到 404；这条路径没有磁盘删除操作。

## 关键代码一：协议与 I/O 解耦

[HttpParser.hpp](../../src/http/HttpParser.hpp#L26)：

```cpp
ParseState consume(std::string_view chunk);
```

接口只接收字节视图，不接收 socket。调用者可以传入网络数据，也可以传入测试字符串；增量状态由解析器自身保存。理解这个边界，就能解释为什么大部分解析测试不需要运行服务器。

## 关键代码二：分隔符跨片与剩余字节

[HttpParser.cpp](../../src/http/HttpParser.cpp#L55) 保留三字节重叠搜索位置；[Connection.cpp](../../src/net/Connection.cpp#L176) 则保留下一请求的数据：

```cpp
pending.assign(parser.leftover());
```

前者解决“一个请求的头部跨多次 receive”，后者解决“一次 receive 含多个请求”。两者必须一起存在，才能处理 TCP 的字节流语义。

`leftover()` 是 string_view，复制进 pending 也解决了当前解析器析构后的生命周期问题。

## 关键代码三：路由 handler 的统一签名

[Router.hpp](../../src/routing/Router.hpp#L13)：

```cpp
using RouteHandler = std::function<HttpResponse(const HttpRequest&)>;
```

路由表不需要知道最终是用户 API 还是文件处理器，只负责选择函数。`dispatch()` 自身使用可修改的请求引用，是因为它要先写入 `params`；handler 接收 const 引用，则只读取填好的请求。

## 关键代码四：socket 的任务捕获

[Server.cpp](../../src/server/Server.cpp#L90) 的片段：

```cpp
auto socket = std::make_shared<TcpSocket>(std::move(*client));
const bool queued = pool_->submit([this, socket, peer] {
    const ConnectionContext context{config_, router_, metrics_, running_};
    serveConnection(std::move(*socket), peer, context);
});
```

这里同时处理两个约束：std::function 的可复制要求和 socket 的独占句柄所有权。上下文在任务内部构造，避免引用接收线程栈上的短命对象。不要误读为多个线程共享读写一个 socket。

## 关键代码五：条件变量与任务锁的范围

[ThreadPool.cpp](../../src/threading/ThreadPool.cpp#L61) 的等待条件：

```cpp
available_.wait(lock, [this] { return stopping_ || !queue_.empty(); });
```

条件为真后，仍在锁内取任务，但 `task()` 在锁外执行。阅读时跟踪两个大括号的范围，比只认识 mutex 和 condition_variable 的名称更重要：锁若覆盖网络读写，所有工作线程就会被队列锁串行化。

## 关键代码六：停止顺序与引用有效性

[Server::stop](../../src/server/Server.cpp#L50) 先把 running 设为 false，再 join 接收线程，然后 shutdown 线程池，最后关闭监听 socket。

先 join 接收线程可确保线程池停止接收任务后不会仍有生产者提交；join 工作线程后，Server 内的 Config、Router、Metrics 才能安全进入析构。原子停止标志负责通知意图，join 才负责等待线程完成和结束对象使用。

## 关键代码七：HEAD 与响应长度

[Connection.cpp](../../src/net/Connection.cpp#L161)：

```cpp
const bool includeBody = request.method != Method::Head;
const bool written = writeResponse(socket, response, includeBody, metrics);
```

HEAD 没有把 `response.body()` 清空，而是告诉序列化器不要输出正文。这样 Content-Length 仍代表对应 GET 正文的字节数。清空正文会使重新计算的长度变成 0，不能表达当前设计的语义。

要继续追问这条语句的作用范围：它在解析成功之后，独立错误路径并未复用这个判断。
